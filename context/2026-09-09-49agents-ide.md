## 是做什么的（如实复述，不评价）

把传统 IDE 里的"终端标签栏 + 分屏"换成一张**无限缩放的 2D 画布**：agent、终端、repo、远端机器都变成画布上的"物件"，用户自己拖拽摆放位置。

核心机制是**真实 tmux 会话**（不是模拟终端）通过 ttyd 暴露在 Web 端，画布上每个 pane 都是一个活跃的 tmux session。Agent 在 pane 里跑 Claude Code / Codex 等 CLI 工具，pane 会随状态变色——蓝色表示 Claude 在工作，朱红色表示需要人工授权。

可以连多台机器（家用 PC / AWS / MacBook）通过 Tailscale 或自托管中继，零 SSH 在同一张画布上打开远端终端。从手机浏览器也能访问同一画布。

## 解决什么问题（事实层面，不判断值不值得解）

- **上下文疲劳（context fatigue）**：创始人 Latif 自述同时跑最多 15 个 CLI 跨多 repo，"忘了哪个 terminal 在做什么"是主要生产力税
- **标签栏和分屏不够用**：传统 tmux/iTerm 网格分屏到一定数量就难管理，2D 画布支持空间记忆（"把 X 项目的 agent 放在画布左下角"）
- **跨机器 agent 编排**：不用 SSH 进出多台机器，所有远端 agent 集中到一张画布
- **移动场景**：在咖啡厅用手机也能看到家里的 agent 状态，不需要专门开电脑
- **AI 用量观测**：内置 HUD 显示 CPU/RAM/Claude API 用量，替代部分外接 observability 需求

## 怎么做的（技术原理/机制，事实层面）

- **画布层**：基于浏览器的无限 2D 画布，物件可拖拽/缩放/分层群组
- **终端层**：每个 pane 是真实 tmux session，通过 ttyd（Web 端的 tmux 暴露工具）输出完整 ANSI 颜色和 scrollback
- **多机层**：每台机器跑一个 agent（49ctl），通过 WebSocket 中继连到主画布；终端 I/O 中继但不持久化
- **访问层**：Tailscale / LAN / 自托管中继三种连接方式；浏览器访问 `localhost:1071` 或托管域名
- **状态可视化**：pane 颜色随 agent 状态变化（蓝色=工作中，朱红=需授权）
- **协作层**：企业版的 coworking 模式支持多人共享画布（具体实现未披露）
- **技术栈**：tmux 3 · ttyd · WebSocket · Monaco 编辑器（嵌入画布的文件编辑） · Tailscale · Node.js ≥18 · Claude Code · Codex
- **失败/错误处理**：未公开文档说明，画布拥挤时的应对见评论区（缩放后当状态指示器使用）

## 关联信息 / 生态

- **与终端复用器（tmux / Zellij）的关系**：tmux 是底层组件，画布是 tmux 之上的空间管理层；不是替代 tmux，而是给 tmux 加 GUI
- **与 VS Code 的关系**：嵌入 Monaco 编辑器（VS Code 同款），但定位不是替代 VS Code，而是管 agent 的 CLI 工作流
- **与 ComfyUI / Langflow / n8n 的关系**：方向不同——后者是"画布上拖节点拼 AI 工作流"，49 是"画布上摆真实运行的 terminal/agent"。前者编排逻辑，后者编排进程
- **与 Claude Code / Codex 的关系**：原生支持 Claude Code 和 Codex（GH topics 标注），pane 状态感知 Claude API 用量

## 评论区反馈（事实摘录，不评价）

- **Latif Alp Adur（创始人，14 票）**："I have been trying to parallelize agentic coding to extreme, sometimes managing up to 15 CLIs at the same time across multiple repos and tasks, and I suffered a huge productivity tax due to context fatigue and constantly forgetting which terminal is doing what. I felt restricted by most grid pane managers, and thats why I started building 49 IDE."
- **Dog Ihno（5h，2 票）**：Beads（任务调度模块）是调度模型还是只是另一个 pane？能否实现"拿所有无依赖的就绪 issue，各分配一个 agent session"？
  - **Murad Ismayilov（创始人）回复**：today it's closer to integrated task context than a giant autonomous scheduler. but what you're describing is exactly why Beads is interesting to us.
- **Julian Ting（6h，2 票）**：几十个活跃 agent 时画布会不会太挤？
  - **Murad 回复**：the canvas is zoomable so you can zoom out and treat terminals more like status indicators than terminals you need to read.
  - **Latif 补充**：That is the whole point!! The canvas is so flexible that there are infinite ways to cluster things around.
- **Rabnoor Singh（5h，2 票）**：拥挤问题是真问题，每个空间工具到 30 个物件左右就崩。
- **Selin（5h，2 票）**：用 crux 做 agent 时主要问题不是 terminal 复用，而是 context 复用（与创始人痛点同向）。
- **Gal Dayan（5h，1 票）**：15+ agent 时在 2D 地图上 panning/zooming 找卡住的 agent 本身就会疲劳。
  - **Latif 回复**：the fatigue, for me and our users, is usually caused not by many agents or navigation itself, but more so forgetting where to navigate.（设计立场：疲劳的根源是"忘了去哪"，不是"导航本身"）
- **Abdullah Guluzada（8h，1 票）**：希望能关闭机器遥测（CPU/RAM/GPU），已经有专门的 observability 工具了。
