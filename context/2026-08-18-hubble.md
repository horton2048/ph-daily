## 是做什么的（如实复述，不评价）

Hubble 自我定位为"the records layer for healthcare"——一个把分散在 EHR / Payer / HIE 系统里的患者病历归并、通过单一 API 返回给 AI agent 或上游应用使用的统一病历层。核心卖点是用"API-only 工具覆盖不到的长尾数据"做差异化：当一个 patient 经一次身份验证后，Hubble 在 API 拿不到数据时，会调度 **browser agent** 登录 provider portal 提交申请、用 **voice agent** 致电 provider 的 records 部门按患者授权请求记录，必要时退回 fax 提交作为兜底。每条返回的字段都带源系统标注，整套调用审计可追溯。

产品分两条线：
- **Patient-Mediated Access（已 Live）**：基于患者"right of access"法定权利代患者取记录，无需 per-provider 数据合同；输出结构化记录、确定性 ID、完整 audit trail；患者可随时审阅 / 撤销。
- **Provider-Mediated Access（Beta）**：经授权直接读写 EHR 与 Payer portal，覆盖实时 eligibility、benefits、prior auth、scheduling、claims、document upload 等场景，与 patient-mediated 同一套 API。

## 解决什么问题（事实层面，不判断值不值得解）

- 标准 FHIR / 网络 API 覆盖不到"长尾"系统：Hubble 官网称美国医疗记录散落在 "fax lines, phone trees, and portal logins nobody remembers"，API-only 工具对这些系统留白。
- 集成多家 EHR / Payer 通常要数月工程 + 每家单独签数据合同，Hubble 主张 "no months of engineering or per-vendor data deals"。
- AI agent（医疗 / 保险侧）拿不到完整患者上下文：Hubble 输出格式直接面向 AI agent 消费，deterministic IDs 便于跨源拼装。
- 目标场景：数字健康应用、保险科技公司、医疗服务方需要跨 provider 聚合患者历史。

## 怎么做的（技术原理/机制，事实层面）

- **接入面**：一次性接入后，Hubble 拉通 EHR、Payer、HIE 网络；官网披露覆盖 **70,000+ 接入系统**。
- **EHR 支持**：Epic、athenahealth、Oracle Health（Cerner）。
- **Payer 支持**：UnitedHealthcare、Aetna、"+ more"。
- **取数三种手段**：① 标准 API 直连；② Browser agent 登录 provider portal 自动提交 request；③ Voice agent 致电 records 部门按患者授权请求；fax 作为兜底。
- **数据治理**：每个值带源系统标记；每条调用 logged、audit-ready；patient-mediated 支持患者移除任意记录、随时撤销访问。
- **身份验证**：用 Persona 做一次性 patient identity verification。
- **Voice 栈**：Deepgram（语音）、Telnyx（电信基础设施）—— 来源 PH "Built with"。
- **HIPAA**：官网明确"every action is permissioned, logged, and HIPAA-compliant from day one"，未公开具体 BAA 文档或第三方审计报告。
- **失败处理（评论区披露）**：voice agent 遇非脚本化问题会 escalate 到人工；prompt 持续迭代；支持 callback queue 跟进；caller ID 在探索动态 / 本地化以提升接通率。
