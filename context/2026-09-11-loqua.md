## 是做什么的（如实复述，不评价）

一个 **macOS / Windows 上的 AI 语音助理客户端**，声称对标 Wispr Flow / Granola / Otter.ai / Apple Intelligence 的合集：把语音转文字、屏幕理解、语音指令执行、TTS 朗读四件事压进同一个客户端。

**核心工作机制**：按住一个全局快捷键说话，语音被上传到 Loqua 自研的全 omni 模型处理，去掉填充词、修正语法、按当前 app 调语气，结果直接光标位置输出。同一模型也看屏幕——用户可以截图任意元素 + 语音提问，不用切应用就拿到答案。

**典型口号**："One shortcut. Any app. Zero delay." 官方宣称速度 220 wpm（vs 传统键盘 45 wpm）。

## 解决什么问题（事实层面，不判断值不值得解）

- **打字速度瓶颈**：220 wpm vs 45 wpm（官方数据）；填充词/口癖自动清除；首稿、长邮件、改稿场景被点名
- **「文档恐惧症」**：官网引用 ADHD 用户自述"空白文档让我卡死"——语音是绕过空白文档的方法之一
- **应用间切换税**：「Capture to Ask」专门为此设计——截图 + 语音问，不离开当前 app
- **跨语言写作**：英语非母语用户可以用母语口述，输出"听起来像 native"的英文（Yuki Tanaka 案例）
- **重复性损伤（RSI）**：官网点名 RSI 用户用 Loqua 替代键盘
- **会议纪要 / PRD / sprint recap**：和 Granola 直接对位，但 Loqua 用通用听写而非专门的会议模式
- **终端 / IDE 写代码注释**：用户 Ryan Cho（Senior Software Engineer）证实在 Terminal / Slack / Notion 都用

## 怎么做的（技术原理/机制，事实层面）

- **模型层**：自研"full omni model"——团队反复强调不是 wrapper，语音和屏幕 share the same context（同一上下文窗口）
- **Tokenizer / Codec**：自研多模态 tokenizer + 自研 codec（官网 + 工程博客均提及）
- **推理位置**：服务端为主（"server-based so you don't have to worry about battery life"——创始人评论原文）；端侧模型在 roadmap
- **隐私声明**：零云端数据保留 + 不用于训练 + GDPR 合规 + 本地历史存储（定价页共同声明）
- **架构博客**：官方博客列出过「three-model stack」架构（2026-04-13 文章标题），但本次未取回细节
- **多语言**：100+ 目标语言；支持句中语言切换（mid-sentence language switching）
- **集成**：全局快捷键在 ~40 个 app 里有定制行为——Google Docs / Word / Notion / Slack / Gmail / Figma / VS Code / Teams / Obsidian / Cursor / Claude Code / 终端等
- **配套能力**：TTS 朗读（Podcast Read-Aloud）、Command to Go（语音触发系统动作）、Dictionary（专有名词库）
- **路线图**：会议转写、多模态扩展、Skill Market、Team 管理、移动端
