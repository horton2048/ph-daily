## 是做什么的（如实复述，不评价）

witr 是一个用 Go 写的命令行 + TUI 工具，回答"这个东西为什么在运行"。给定一个进程名 / PID / 端口 / 容器 / 文件锁，它会把该进程的**祖先链**（ancestry chain）一路回溯到启动它的源头——systemd unit、launchd 服务、cron、SSH 会话、Docker 容器、pm2、Snap/Flatpak 沙盒、交互式 shell 等——并标出沿途的告警。

核心理念是把"端口、服务、容器、命令"都统一归约为一个 PID 问题，再为这个 PID 构造一条因果链：什么在跑、怎么起来的、谁让它持续运行、它属于什么上下文。

形态：单一静态 Go 二进制，Linux/macOS/Windows/FreeBSD 全平台。无参数启动进入 TUI（Processes / Ports / Containers / Locks 四个 tab）；带参数则是脚本友好的 CLI（`--short` 单行输出、`--json` 带 exit code）。

## 解决什么问题（事实层面，不判断值不值得解）

- **"这进程哪来的"没有趁手工具**：作者自述 witr 来自一个反复出现的烦躁——发现某个东西在跑，却没有工具能解释它为什么在那（PH 评论区 maker comment）。
- **现有工具只答"在跑什么"，不答"为什么在跑"**：`ps`/`top`/`lsof`/`ss` 列状态，但不还原启动来源、时间、责任系统和告警链。
- **生产排障/事件响应场景**：服务器上看到陌生进程、端口被占、容器在重启、文件被锁——需要快速判断"是 systemd 拉的、cron 起的、还是被注入的"。仓库 topics 自标 incident-response、observability、sysadmin、troubleshooting。
- **安全视角的异常信号**：以 root 跑、绑 0.0.0.0、二进制已删除、LD_PRELOAD 被设置、重启循环——这些"非阻塞观察"被单独标为 warnings。

## 怎么做的（技术原理/机制，事实层面）

- **单一静态 Go 二进制**，Apache-2.0 协议，全平台一套二进制。
- **回溯机制**：不只走 ppid 链，而是结合进程 cgroup 来识别归属的 systemd unit（Linux 上）。容器场景穿透到宿主：systemd → containerd-shim → 容器进程。
- **目标归一化**：端口/容器/文件最终都映射到 PID，再构造因果链。
- **Linux 数据源**：读 `/proc/locks` 做 fcntl/POSIX 与 BSD flock 锁检测；读 `/proc/<pid>/stat`（含 session ID、TTY 等字段，作者在评论里确认可用来识别 nohup/setsid/tmux 主动脱离的进程）。
- **跨平台数据源**：macOS 用 `ps`/`lsof`/`sysctl`/`pgrep`；Windows 用 ToolHelp32/PSAPI/Service Control Manager；FreeBSD 用 `procstat`/`ps`/`lsof`。
- **告警类型**：以 root 运行、非 root 进程持有危险 Linux capabilities（CAP_SYS_ADMIN 等）、绑定 0.0.0.0/::、多次重启（超阈值）、RSS > 1GB、运行 > 90 天、二进制已删除、LD_PRELOAD/DYLD_* 注入迹象。
- **PID 复用防护**：TUI 对进程执行动作（kill/terminate/pause/resume/renice）前，会比较进程 start time 防止 PID 复用误伤。作者在评论区承认父 PID 链回溯阶段的 PID 复用是已知风险，已立 issue。
- **退出码**：0 clean / 1 warnings / 2 not found / 3 permission denied / 4 invalid input / 5 internal error。PH 评论区 Asad M. 提议把"无法判定"独立为 exit code 2，作者已收到该反馈。
- **只读**：所有操作只读，作者明确"生产环境安全"。

## 评论区反馈（事实摘录，不评价）

- **Rabnoor Singh**：追问 orphan 检测——accidental orphan 与主动脱离（nohup / setsid / tmux）如何区分。作者回复：session ID 与 TTY 已在 `/proc/<pid>/stat` 解析切片里，可支持该特性。
- **Asad M.**：提议为"无法判定"场景单独设 exit code（0 resolved / 1 error / 2 unknown），而非把不确定性塞进 success。作者收到。
- 作者自述局限：当前 bare orphan（无 supervisor 的进程）会错误归因其来源；上线当天已立 bug。父 PID 链回溯阶段的 PID 复用是已知风险，已立 issue。
- 作者谈命名："witr 来自 frustration 而非一个 claim"，真正的"why"（这东西还该不该跑）"lives outside the box entirely"——即工具只回答因果链，不替人判断该不该留。
