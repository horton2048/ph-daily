## 是做什么的（如实复述）

Xirp 是一个 agentic 开发环境，核心卖点是"机构记忆（institutional memory）"。它连接企业内部的服务目录、归属（ownership）、文档和架构决策记录，把这些上下文喂给 AI 编码会话，使 agent 不再只看当前文件，而是带着整个系统的背景工作。

按官网结构，产品有四个面：
- **Agent** — agentic 开发环境本体，能看到 ownership、依赖、设计 rationale。
- **Workspace** — Portal 内的插件，把工作项、会话、文档放一处；一个工程师的会话上下文"存下来，给下一个人或下一个 agent 用"。
- **Documentation** — 从编码会话中自动生成、持续更新的活文档，反哺未来会话。
- **Flexibility** — 模型无关 harness，支持 Claude / Gemini / Codex，可在会话中途切模型而不丢上下文，也支持自托管开源模型。

PH hunter Chris Messina 补充的运行方式要点：
- 可同时跑 50+ 并行 agent 会话，跨不同 harness，每个会话有独立但可移植的 worktree 与上下文。
- vendor-neutral，可在任务进行中切换模型以优化价格-性能比。
- 接上 Portal 后，Xirp 注入组织上下文（架构、依赖、归属、决策），会话数据回流 Portal 供跨团队复用与可见。
- Chris Messina 称其最近对标对象是 Craft Agents（已被 Polymarket acquihire）。

## 解决什么问题（事实层面）

- agent 只看当前文件、不懂"这个服务谁维护、为什么这么设计"——上下文缺失导致建议跑偏。
- 多人/多 agent 反复重新建立同一套背景知识，没有沉淀机制。
- 模型锁定：换模型就要丢上下文重开会话。
- 跨团队工作不可见：A 团队的 agent 会话结果 B 团队拿不到。

## 怎么做的（技术原理/机制，事实层面）

- 索引企业内部系统（services、models、catalog）构建上下文层。
- 与 Portal 集成后，surface ownership、dependencies、architectural decisions 到每次编码会话。
- 会话知识被自动捕获为文档，形成"上下文复利"——每个新会话从累积的机构上下文起步。
- model-agnostic harness 支持中途切模型（Claude / Gemini / Codex / 自托管开源模型），上下文不丢。
- 并行会话用独立可移植 worktree 隔离，支持 50+ 并发。
- Portal 本身与 Spotify 开源的 Backstage（已捐 CNCF，graduated 项目）同源/演进关系——Backstage 是开源 IDP 框架，Portal 是 Spotify 私有生产实例。Xirp 站在 Portal 之上做 agent 层。
